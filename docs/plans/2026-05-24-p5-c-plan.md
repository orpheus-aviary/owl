## 1. 背景与目标

### 1.1 P5-b 留下了什么

P5-b 已 ship 内部，多 entity apply + SSE 实时 + GUI sidebar 状态栏齐了，自动化 dual-profile e2e D1-D10 全绿。但还有 4 块明确缺口让"内部能跑"和"对外能发"之间隔着一道：

1. **同步只有 SSE + 手动** — server 关掉 SSE / 网络抖一下没有兜底；定时拉取没做；网络恢复没听
2. **HTTP 错误硬失败** — `runSync` 遇到 429 / 5xx 直接 throw、status 翻 error 等下一次 SSE 才再试；没有 retry + jitter，可能把 server 打更狠
3. **冲突静默** — LWW lose 的本地修改直接被覆盖，用户连"发生过冲突"都不知道；`conflict_record` 表自 P4 Phase 2 起一直空着
4. **明文 token** — `skybridge_config.toml` 的 `[auth].token` 是明文存盘，跨设备拷 toml 就能盗用

外加 P5-b 手动验收 + 用户使用反馈共 7 个小尾巴（G1-G7），数据正确性 / UX polish 各占一半。

### 1.2 P5-c 一句话

把 P5-b 的 SSE+手动 触发链路扩成 **多源后台 sync（SSE + 定时 + onError 退避期探针）+ retry/jitter + 冲突可见 + token 不泄漏**，叠加 G1-G7 收尾，本地 UI 手动测试 + 自动化 e2e 全绿即发 **0.5.0**。

### 1.3 必证四条（0.5.0 发版门槛）

1. SSE 关闭后定时 sync 兜底（默认 5 min interval，可配置）；SSE onError 退避期间 10s `/health` 探针成功立即重连
2. 429 / 5xx 走 retry 策略（指数退避 + jitter，`maxRetries=5`、6 attempts），retry 期间不翻 status 到 error
3. apply 路径远端覆盖本地 note 且 content 实际不同时 `conflict_record` 落一行（`losing_side='local'`），GUI sidebar 有红点 + 列表 + 查看本地版本副本 + 软删忽略
4. token 不泄漏：`skybridge_config.toml` 在 unix 系统上 `chmod 0600`、日志全量 mask、sidebar popover / 任何 UI 都不显示原 token；keychain 加密推到 P5-d

### 1.4 不做（推到 P5-d 或更后）

- **真实双机 + 远程 server soak** — 0.5.0 之后单独阶段讨论
- **keychain / safeStorage 加密 token** — 当前 login 走 daemon `/sync/login` 写 toml，daemon 进程没有 Electron 上下文；路 A（login 迁 main IPC，破坏 CLI）/ 路 B（半加密状态机 + 文件改写订阅）都需要 auth 架构级改动，与 P5-d 真实双机 / token refresh / device pair / CLI headless 是同一套问题，**P5-c 不开**。0.5.0 走 chmod 0600 + log mask + UI mask 兜底
- **冲突解决 UI（恢复本地 / merge / diff viewer）** — A 阶段只 view-only + 软忽略，B/C 留 P5-d / 0.6.0
- **多类型冲突写入**（delete / folder move / tag） — A 阶段只写 note update apply 远端覆盖本地；helper 设计成开放 dispatch，B 阶段加分支即可
- **SSE idle watchdog** — 不假设「server 长期不发任何 event 时本地主动断重连」；watchdog 会让静默 workspace 周期性重连，需要 server 端 keepalive ping 配合，留 P5-d 看真实双机数据再决定阈值
- **attachment 通道 / snapshot 拉取 / 多 workspace 切换** — 留 P6
- **Conversation message-level dedup** — P5-b 决策保留「两份」，0.5.0 不改

#### 2.2 后台 sync 触发

新增**两个**后台触发源（SSE 在 P5-b 已落地，是第三源）：

- **定时触发**：daemon 启动期 `setInterval` 调 `runManualSync`，默认 5 min，从 `owl_config.toml` 的 `[sync].interval_min` 读（不存在则默认 5）。`<= 0` 表示禁用，min clamp 到 1。**与 `[daemon].poll_interval_min` 完全独立**（后者是 reminder scheduler 用，不是 sync；实现时不要复用）。生效条件与 SSE bridge 一致：`[auth]+[device]+[workspace]` 全在 toml 才启动
- **onError 退避期探针**：仅在 SSE bridge `onError` 触发后到下次重连尝试的退避窗口内启动 **10s** `/health` 轻量探针；探针成功立即 cancel 退避计时器、强制 SSE 重连，SSE `onOpen` 自带 catch-up sync 跑一次。**只覆盖显式 disconnect 路径**，不假设「server 长期不发任何 event 也能恢复」——后者需要 server keepalive + client idle watchdog 配合，留 P5-d。**探针周期改 10s 不是 30s 的原因**：SSE backoff cap 也是 30s，30s 探针 vs 30s SSE 自重连基本不加速；10s 探针在 SSE 进入 30s 退避期时能有 2-3 次机会先于 SSE 自重连恢复

`runManualSync` 已有 coalescer（F3 `615e233`），三源叠加不会重复打 server。

#### 2.2-bis 后台 handles 的 mid-session 启停（P5-b 留的口子）

P5-b `bridge-lifecycle.ts:15` 显式把「daemon 已运行时用户首次 `owl sync login` + `owl sync run` 完成，config 从 incomplete 变 complete」这个 mid-session bootstrap 留给 P5-c。**当前行为**：boot 时检测 toml 不完整 → silent skip auto-start → 用户登录 + 首次 sync 写 device/workspace 进 toml 后，SSE bridge / 定时 sync / health-probe 都**还是没启动**，必须手动 `just stop-daemon && just dev-daemon` 重启才行。

P5-c 修法：

- **入口**：`packages/daemon/src/sync/manual.ts:187` 的 `doRunManualSync` 在 `ensureSkybridgeSession(ctx)` 成功**且**本次是 first-success（即上次启动时 `bridge-lifecycle` 判定 incomplete 跳过过）时，调一个新的 `ensureBackgroundHandles(ctx, logger)`
- **`ensureBackgroundHandles`** 负责（幂等）：
  - 如果 SSE bridge handle 不在 ctx，调用 `startSseBridgeIfBootstrapped(ctx, logger)`（P5-b 已有，本身幂等）
  - 如果 scheduler handle 不在 ctx，启动 §2.2 定时 sync
  - health-probe 由 SSE bridge `onError` 驱动，不需要 mid-session 单独启
- **handle 存储**：ctx 加可选字段 `sseBridge?: { stop(): void }` / `syncScheduler?: { stop(): void }`；`cli.ts:156` shutdown 序列读 ctx 字段 stop，与 reminder scheduler 并列
- **不变量**：mid-session 启动只走「incomplete → complete」单向迁移；complete → incomplete（删 toml / 登出）不做 mid-session stop，留 P5-d 与 logout 流程一起设计

#### 2.3 429 / 5xx retry 策略

- **位置**：`packages/core/src/sync/engine.ts` `runSync` 调 `client.push/pull` 处包 `withRetry`
- **策略**：`maxRetries=5`（6 attempts 总），退避 `[1, 2, 4, 8, 16]s` + 0-500ms jitter；只对 429 / 5xx / `NetworkError` retry；4xx 其它直接 throw（401 也直通，不进 retry）
- **命名**：代码统一用 `maxRetries`（首次 attempt 不算 retry），不要混入 `maxAttempts`
- **错误传播（关键）**：`withRetry` 失败后**抛最后一次原始错误**（`ApiError` 保留 `.status` / `NetworkError` 保留 cause），**不能包成新的 `RetryExhaustedError`**——否则 daemon `manual.ts:130` 的 `translateSkybridgeError` / `statusForError` 会丢 `ApiError.status`，429 / 5xx 被翻译成 generic 500，markError 写入的 `last_error` 也错。retry 次数 / 间隔只在 daemon log 记，不进抛出的错误本身
- **状态可见性**：retry 期间 `sync:status_changed` 不切到 `error`，保持 `syncing`；retry 全部失败才翻 `error` + `last_error` 写入；中间 retry 次数 / 间隔在 daemon log（不进 UI，避免吓人）
- **与 SSE 重连退避独立**：SSE bridge 自己的 `[2,4,8,16,30]s` 退避不变，retry 只管 HTTP push/pull

#### 2.4 conflict_record 方案 A（薄）

**Schema 变更**（migration 0007）：

```sql
-- 0007_conflict_record_payload.sql
ALTER TABLE conflict_record ADD COLUMN losing_side TEXT;
ALTER TABLE conflict_record ADD COLUMN local_payload TEXT;   -- JSON
ALTER TABLE conflict_record ADD COLUMN remote_payload TEXT;  -- JSON
ALTER TABLE conflict_record ADD COLUMN local_updated_at_ms INTEGER;
ALTER TABLE conflict_record ADD COLUMN remote_updated_at_ms INTEGER;
CREATE INDEX idx_conflict_unresolved ON conflict_record (resolved_at) WHERE resolved_at IS NULL;
```

**不加 CHECK constraints**（前向兼容 B/C 的 `'restored' / 'merged'` resolution 值）。

**写入触发点**：`packages/core/src/sync/engine.ts` `applyNoteChange` 的 **op='update' apply 远端覆盖本地** 分支（`localTs < remoteTs`，远端将写入本地表）调 `recordConflict({ entityType:'note', entityId, losingSide:'local', localPayload, remotePayload, localUpdatedAtMs, remoteUpdatedAtMs })`，**且必须 content 字段实际不同**（避免 noop 噪音）。

**不写入的两个反例（重要）**：
- `localTs >= remoteTs` 的 LWW skip 分支 —— 远端被丢弃、本地完好，没有任何"本地丢失版本"语义
- self-replay（cid 命中 P5-a self-replay skip）—— 自己 push 的 change 自己拉回来不进 LWW 判定
- delete / restore / folder / conversation —— A 阶段都不写；helper 是开放 dispatch，B 阶段在新分支调同一 helper

`losing_side` 在 A 阶段固定 `'local'`；`'remote'` 留 B 阶段「以本地覆盖远端」反向 push 时使用（"查看本地版本副本" UX 与之不在同一 widget）。

**losing local outbox 仍会 push（已知 + 接受的语义）**：当前 `runSync` 先 pull 后 push（`engine.ts:701` / `:741`）；B 本地旧修改被 A 的远端新修改 apply 覆盖、写一行 conflict_record 之后，**B 本地 outbox 里那条 pending `sync_changes` 仍会在同一轮的 push 阶段送上 server 历史**。其他设备拉到时会因 LWW（`localTs >= remoteTs` skip）丢弃，不会改写它们的本地表，但 server log 里会留下这条 losing change。**P5-c 不做 outbox suppression**：清理 outbox 牵涉到「conflict 记录后是否该撤销本地 emit」「sync_changes 死信处理」等独立设计点，且现状不破坏跨设备一致性，留 P5-d 与 server retention 一起重审。

**helper**：`packages/core/src/sync/conflicts.ts`：
- `recordConflict(opts)` — INSERT 一行
- `listUnresolvedConflicts({ limit, offset })` — `WHERE resolved_at IS NULL` 列表
- `ignoreConflict(id)` — `UPDATE SET resolved_at=now, resolution='ignored'`（**软删**，不 DELETE）
- `countUnresolvedConflicts()` — sidebar 徽章用

**daemon API**：
- `GET /conflicts` — 分页列表，返回 `{ id, entity_type, entity_id, losing_side, local_updated_at_ms, remote_updated_at_ms, local_payload, remote_payload, detected_at }`
- `POST /conflicts/:id/ignore` — 软删
- `GET /conflicts/count` — 计数（sidebar 用，也可走 SSE 推）

**事件桥（关键）**：`conflict_record` 检测发生在 `@owl/core` `runSync` apply 路径，但 OwlEvent bus 在 daemon `ctx.eventsBus`，core 不直接接 events bus（保持 P5-b 不变量"core 不知道 events"）。所以：

- `runSync` 返回值的 `RunSyncResult` 扩 `conflictsRecorded: number`
- `packages/daemon/src/sync/manual.ts` 在 `markSuccess` 前若 `conflictsRecorded > 0` 调 `ctx.eventsBus.emit({ type: 'conflicts:changed' })`（注意：是 `emit` 不是 `publish`，对齐 `packages/daemon/src/events/bus.ts:29` 现有 API；event 不带 payload，GUI 自己拉 `/conflicts/count`）
- `POST /conflicts/:id/ignore` 也在 daemon 路由里 `emit` 同一 event
- `packages/daemon/src/events/types.ts` `OwlEvent` union 加 `{ type: 'conflicts:changed' }` 分支
- GUI 端 `packages/gui/src/renderer/src/components/events-subscriber-core.ts` 加 `conflicts:changed` 分支调 `useConflictsStore.refresh()` 或 `bumpConflicts()`
- **`packages/gui/src/renderer/src/components/EventsSubscriber.tsx:41/49` 必须显式 `es.addEventListener('conflicts:changed', ...)`** —— SSE EventSource 按 event name dispatch，当前只注册了 `open_note` + `sync:status_changed`，没有「dispatcher 自动覆盖新事件」机制。可顺手把三处 addEventListener 重构成 `EVENT_TYPES.forEach(type => es.addEventListener(type, ...))` 表驱动，避免下次再漏

**GUI 改动**：
- `SyncStatusBar` 旁加冲突红点 + 计数（0 时不显示）
- 新增「冲突」页（路由 `/conflicts`，sidebar 加入口）：列表 + 「查看本地版本副本」按钮（弹只读 modal，markdown 渲染 local_payload.content）+ 「忽略」按钮（confirm 后软删）
- 入口位置：`packages/gui/src/renderer/src/MainApp.tsx:315` sidebar nav 区在 Trash 上方加一个 ConflictsNav 项，仅在 `count > 0` 时显示（`MainApp.tsx` 直接在 renderer/src/ 下，**不是** `components/` 子目录，nav 是 MainApp 内联）
- **冷启动 count fetch**：`conflicts-store` 在 `MainApp` mount 时调一次 `GET /conflicts/count`（与 `sync-status-store` 启动 fetch 同套路）；GUI 重启后若 DB 里有未解决冲突，红点会立刻出现，不依赖 `conflicts:changed` 事件触发

**不参与 sync**：`conflict_record` 本地状态，detection 因设备而异；不进 `sync_changes`、不 emit、不 push。这条作为**显式不变量**记入 §6 «关键不变量»。

#### 2.5 token 不泄漏（0.5.0 兜底，keychain 推 P5-d）

**目标**：token 仍以明文落盘（不做 keychain），但确保**任何辅助通道都不让 token 泄漏**。完整 safeStorage 加密留 P5-d，与 auth 架构（login 所有权 / token refresh / device pair / CLI headless）一起设计。

**三层保护**：

1. **文件权限**：`packages/core/src/skybridge/config.ts` 写 toml 后调 `fs.chmod(path, 0o600)`（unix 系统；Windows 默认 user ACL 已限制，跳过 chmod）。`writeSkybridgeConfig` 统一加这步，单测覆盖 unix `stat.mode & 0o777 === 0o600`、Windows skip 不 throw。
2. **日志 mask**：`packages/core/src/skybridge/redact.ts` 新增 `redactToken(value: string): string` —— 显示前 4 字符 + `***` + 后 4 字符（短于 12 字符全 `***`）。`packages/core/src/logger/index.ts:20` `createLogger` 接受可选 `redact?: pino.LoggerOptions['redact']` 字段，默认值含 `['*.token', '*.auth.token', 'authorization', 'headers.authorization', 'req.headers.authorization', 'Authorization', 'headers.Authorization', 'req.headers.Authorization']` + `censor: '[REDACTED]'`。**pino redact 大小写敏感**，所以 `authorization` / `Authorization` 两套 path 都要写（HTTP headers 在 fastify 里是小写、但 fetch 调用方手写时常用 `Authorization`）。`createConsoleLogger`（`logger/index.ts:55`）同样加默认值。任何 logger 输出（含 `child`）的 SkybridgeConfig / HTTP headers 都自动 mask。**daemon 没有 `bootstrap.ts`**，所有 wiring 在 `cli.ts` 直接 createLogger 时生效。
3. **UI mask**：sidebar SyncStatusBar popover 与未来任何 settings page **不显示原 token**；最多显示 `redactToken` 输出。当前 popover 不显示 token，写一条 ESLint-style 注释 + 单测断言 popover render output 不含 `cfg.auth.token` 子串。

**文档**：`docs/plans/2026-05-24-p5-c-plan.md` 自身 + `CLAUDE.md` skybridge debug 段明确写"`skybridge_config.toml` 是 local user secret，不要 commit / 不要分享 / 拷文件即获得登录态"。

**P5-d 时再做**：safeStorage 加密 + login 所有权讨论 + token refresh + CLI headless 策略 + token_enc toml 字段。

#### 2.6 自动化 e2e + 手动 UI 测试

- `sync.dual.e2e.ts` 加 4 个新 case（编号紧接 P5-b 的 D10）：
  - **D11**: SSE done:true（G2 集成）— skybridge server 优雅 shutdown，owl client SSE reader 收到 `done:true` → fire onError → 退避重连 → server 重启后 onOpen + catch-up sync

## 3. 关键设计点拍板

### 3.1 后台定时 interval 配置

- 默认 5 min；最小 1 min（避免误填 1s 把 server 打挂）；`<= 0` 禁用
- 来源：`owl_config.toml` `[sync].interval_min`（新增字段，default 5）
- **不**支持运行时动态修改（改 toml + restart daemon 才生效），P5-c 不做 hot reload
- 单测：默认值、最小 clamp、禁用、清空字段回退默认

### 3.2 onError 退避期探针（不承诺"下行卡住"恢复）

- **承诺范围**：仅覆盖 SSE 显式 disconnect / done:true / 网络错误等会触发 `onError` 的路径；**不**承诺 server 长期不发任何 event 这种「连接没断但下行卡死」场景（需要 server keepalive + client idle watchdog 配合，P5-d 再做）
- 触发条件：**仅在 SSE bridge 当前处于退避期**（`onError` 触发后到下次重连尝试之间）才起 **10s** 探针；正常连接期间不探
- 探针周期 10s 而非 30s 的原因：SSE backoff 是 `[2,4,8,16,30]s + jitter`，cap 30s；30s 探针 vs 30s SSE 自重连基本不加速。10s 探针在 SSE 进入 30s 退避期时有 2-3 次机会先于 SSE 自重连恢复
- 探针实现：`fetch(${serverUrl}/health, { signal: AbortSignal.timeout(3000) })`
- 探针成功 → 不等退避计时器，立刻 cancel 退避 + 触发 SSE 重连；SSE `onOpen` 已有 catch-up sync 跑一次
- 探针失败 → 沉默，等下个 10s 周期或 SSE 退避计时器先到（谁快谁恢复，探针失败不阻塞 SSE 自身重连）
- 不影响 SSE bridge 重连退避序列本身（`[2,4,8,16,30]s + jitter` cap 30s 不变）

### 3.3 retry 与 SSE 重连职责分离

| 故障 | 由谁兜 | 退避 |
|---|---|---|
| HTTP push / pull 429 5xx | `withRetry`（§2.3） | `[1,2,4,8,16]s + 0.5s jitter` `maxRetries=5`（6 attempts） |
| SSE stream 断开 / done:true（G2 修后） | SSE bridge 自身 | `[2,4,8,16,30]s + 1s jitter` cap 30s 永不放弃 |
| onError 退避期网络恢复 | §3.2 探针 + 强制重连 + SSE onOpen catch-up | 10s 探针周期 |
| 定时拉取失败 | `withRetry` 已 wrap，失败由 retry 兜 | 同 §2.3 |

retry 与 SSE 重连**没有任何耦合**（仅在 SSE onError 触发后，探针机制临时启动；探针不进 SSE 退避序列）。

### 3.4 conflict 写入条件（单一）

**写**：apply 路径处理 `op='update'` 的 ServerChange，且 `localTs < remoteTs` 决定要用远端覆盖本地，且本地与远端 content 字段实际不同 → 写一行 `conflict_record`，`losing_side='local'`，`local_payload` 保留被覆盖前的本地版本，`remote_payload` 是即将写入的远端版本。

**不写**（重要反例）：
- `localTs >= remoteTs` 的 LWW skip 分支 — 远端被丢弃、本地完好，没有任何「本地丢失」语义
- self-replay（cid 命中 P5-a self-replay skip）— 自己 push 的 change 自己拉回来不进 LWW 判定
- `op='create' / 'delete' / 'restore'` / folder / conversation — A 阶段都不写

losing_side 在 A 阶段固定 `'local'`。`'remote'` 留给 B 阶段「以本地覆盖远端」时使用（"查看本地版本副本" UX 与之不在同一 widget）。

### 3.5 [sync] config section

新增独立 config section，**不复用 `[daemon].poll_interval_min`**（后者是 reminder scheduler 用，与 sync 无关）。

```toml
[sync]
interval_min = 5      # 后台定时同步间隔，<=0 禁用，min clamp 到 1
```

- `packages/core/src/config/index.ts` 加 `SyncConfig` interface + 默认值 `{ interval_min: 5 }`
- parse 时：缺 section / 缺字段 → 默认 5；`<= 0` → 禁用（return 0，daemon 不起 interval）；`> 0 && < 1` → clamp 到 1；**非法（NaN / 字符串）→ 静默回退默认 5，不在 core 层 log**（`loadConfig` 是纯读函数，不依赖 logger）
- daemon `sync/scheduler.ts` 启动时 log 一行 `effective sync interval_min=${value}` 给运维看（info 级，**不是 warn**）；如果想发现非法值，可对比 raw toml 字段做诊断 log，但 P5-c 不做（不复杂化）
- 单测：4 个 case（默认 / clamp / 禁用 / 非法静默回退）

## 6. 关键不变量（P5-c 新增）

> 与 [P5-b shipped §关键不变量](../history/P5-b-shipped.md#关键不变量已落地有测试--守卫保护) 累加，编号从 15 起。

15. **`conflict_record` 不进 sync_changes** — detection-time 本地状态，每台设备 LWW lose 情况不同；不 emit、不 push、不参与 sync engine。helper 设计成开放 dispatch（接受任意 `entity_type` + JSON payload），B/C 阶段加多类型不需要 migration。
16. **conflict 写入条件单一** — 仅 `applyNoteChange` 处理 `op='update'`、`localTs < remoteTs`、content 字段不同 三条**同时**满足时写一行；LWW skip / self-replay / create / delete / restore / folder / conversation 都不写。`losing_side` A 阶段固定 `'local'`。
17. **conflict_record "忽略" 是软删** — `UPDATE SET resolved_at=now, resolution='ignored'`，**绝不 DELETE 行**。前向兼容 B 阶段「已解决历史」需求。
18. **conflict_record schema 无 CHECK constraints** — `entity_type` / `losing_side` / `resolution` 都是 TEXT 开放 enum，校验只在 TS 层；B/C 加 `'restored' / 'merged'` 值不需要 migration。
19. **conflict 事件桥**：`@owl/core` `runSync` 通过 `RunSyncResult.conflictsRecorded` 返回计数；`@owl/daemon` `manual.ts` 在 `markSuccess` 前若 > 0 才 `ctx.eventsBus.emit({type:'conflicts:changed'})`（对齐 `events/bus.ts:29` 的 `emit` API，不是 `publish`）。core 永远不接 `ctx.eventsBus`（保持 P5-b 不变量）。
20. **三源后台 sync 走同一 coalescer** — SSE 触发 / 定时 tick / onError 退避期探针恢复重连 / 手动 POST 全部经 `runManualSync` → P5-a F3 coalescer；不会同时打 server 两次。
21. **HTTP retry 不翻 status** — `withRetry({ maxRetries: 5 })` 期间 `sync:status_changed` 保持 `syncing`，retry 全部失败（6 attempts 都没成功）才翻 `error`；GUI 视觉上对 429 抖动免疫。
22. **SSE 重连退避 与 HTTP retry 退避 独立** — SSE 是连接级故障，HTTP 是请求级故障；两者各自策略 + 各自计时器；仅在 SSE onError 进入退避时启动 10s `/health` 探针作为副产物加速恢复（SSE backoff cap 30s 时探针有 2-3 次机会先于 SSE 自重连）。
23. **onError 退避期探针只覆盖显式 disconnect** — 不假设 SSE 长时间挂着（onError 不触发的下行卡死）能恢复；正常连接期间不探，节省 server 压力；SSE idle watchdog 留 P5-d 看真实双机数据再决定。
24. **`[sync].interval_min` 是独立 config 字段** — 不复用 `[daemon].poll_interval_min`（后者是 reminder scheduler）；缺省 5 / `<=0` 禁用 / `0 < x < 1` clamp 1 / 非法值**静默回退默认 5**（core 层不 log，loadConfig 是纯读函数）。daemon scheduler 启动时 info-log 一次 effective 值给运维看。
25. **mutation 路径填 `notes.device_id`** — 设计 §3.3 P5-b 没落实的 G4，P5-c 落定：`createNote/updateNote/createFolder/updateFolder` 用 `input.deviceId ?? readSkybridgeDeviceId(sqlite) ?? null`；apply 路径仍由 `ServerChange.deviceId` 填（不变）。
26. **mutation 路径触发 `syncReminders`** — `/alarm` tag 出现 / 消失时同步调 `syncReminders`；scheduler 保留作兜底，但不再是单一来源。
27. **token 不入 log / UI / world-readable file** — `skybridge_config.toml` unix 系统 `chmod 0600`（**已在 `config.ts:177` 落地**）；`createLogger` + `createConsoleLogger` 默认 pino redact `*.token` / `authorization`（结构化字段自动盖）；**字符串拼接靠 grep 守卫 + 仓内约定**（pino redact 盖不住模板字符串里的 token）；任何 UI（包括 sidebar popover）不显示原 token。完整 safeStorage 加密留 P5-d，那时 login 所有权 / token refresh / device pair 一起重设。
28. **`withRetry` 失败抛原始错误** — 不包成 `RetryExhaustedError`；`ApiError` 保留 `.status`、`NetworkError` 保留 cause，确保 daemon `manual.ts:130` `translateSkybridgeError` / `statusForError` 能正确翻 HTTP status；retry 次数 / 间隔只进 daemon log 不进抛出错误本身。
29. **conflict losing local outbox 仍 push（接受语义）** — `runSync` 先 pull 后 push（`engine.ts:701/:741`），B 端 apply 远端覆盖本地 + 写 conflict 后，本地原 outbox 那条 pending `sync_changes` 仍会同轮 push 上 server log。其他设备靠 LWW skip 不会改写本地表，但 server log 会留这条 losing change。**P5-c 不做 outbox suppression**，留 P5-d 与 server retention 一起重审。
30. **GUI 新增 OwlEvent 必须在 `EventsSubscriber.tsx` 显式 addEventListener** — SSE EventSource 按 event name dispatch；当前只注册 `open_note` + `sync:status_changed`，新增 `conflicts:changed` 必须显式注册（建议同步重构为表驱动），否则事件永远到不了 `events-subscriber-core.ts` dispatcher。
31. **后台 timers 必须有 stop handle + unref** — 新增 scheduler / health-probe 全部 `setInterval(...).unref()`，启动返回 `{ stop() }`，接进 `cli.ts:112` shutdown 序列；teardown 后无 dangling timers，避免 daemon hang exit / 测试残留计时器。
32. **mid-session bootstrap 单向** — daemon 运行期间 toml 从 incomplete 变 complete（首次 login + sync run）时通过 `ensureBackgroundHandles` 拉起 SSE bridge / scheduler，幂等。**反向（complete → incomplete）不在 P5-c 处理**，留 P5-d 与 logout 流程一起设计。boot 路径不变（P5-b 行为保留）。
33. **GUI conflict count 必须有冷启动 fetch** — `conflicts-store.refresh()` 在 `MainApp` mount 时拉一次 `/conflicts/count`，不依赖 `conflicts:changed` 事件触发；否则 GUI 重启后已有未解决冲突时红点不会显示。

## 8. 风险与回退

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 0007 migration ADD COLUMN 失败 | 字段名冲突 / sqlite 拒 | 5 列全 NULL-able + 加 index；旧行 payload 字段 NULL，GUI 显示 "(无副本)"；migrate runner 单测覆盖空表 + 有 P4 占位行两种 |
| onError 退避期探针打 server 太频 | 多 owl 实例同时进入退避 | 10s 周期；server `/health` 是匿名轻量端点；探针仅在退避期跑（正常连接不探），bridge 重连成功立即 stop；最坏每客户端在 30s 退避窗口内 3 次 `/health` |
| Retry 把 502 类暂态打成永久失败 | server 长时间 5xx | 6 attempts 后翻 error，依赖定时 5 min / SSE onOpen 接下来重试；不会无限重 |
| conflict_record 列表过大撑爆 sidebar count query | 用户长期不处理冲突 | sidebar 红点 cap 显示 `99+`；列表分页 50；count 查询用 §2.4 `idx_conflict_unresolved` partial index |
| G1 preload argv 注入跨 Electron 版本不稳 | electron 升级 `additionalArguments` 行为变 | renderer 兜底回 `http://127.0.0.1:47010`；M4 手动验通过 |
| G2 done:true 修后旧 server 行为依赖 | skybridge server 端 graceful shutdown 改 fire `event: bye` | owl 端只多一次 onError → 退避 → 重连，无副作用 |
| chmod 0600 在某些文件系统不生效 | NFS / FAT / Windows / WSL | unix 仅 unix；Windows skip；NFS / FAT 上 mode 可能被忽略但不 throw，保险起见 log debug |
| pino redact 漏 path | 手写 log 直接拼字符串绕过 redact | grep daemon 全仓 `\.token\b` / 字符串拼接日志；CI 加 lint 规则 |
| 0.5.0 发版 macOS Sequoia codesign 又出问题 | electron-builder afterPack 钩子没跟新版 | 0.4.1 已稳；release 流程不动；出问题回 0.4.1 |

**回退路径**：
- 任意 step 失败可单独回退该 commit；step 间无强依赖（除 Step 13 依赖 Step 12 schema）
- 0007 migration 是纯 ADD COLUMN，无需 down migration（旧版本 schema check 触发 LATEST_KNOWN_VERSION 比对会拒，但 0.5.0 不允许降级到 0.4.x）

## 9. 一句话总结

P5-c = 7 个 G 收尾 + 3 源后台 sync（SSE / 定时 / onError 探针）+ HTTP retry（maxRetries=5）+ conflict 方案 A + token 不泄漏三层（chmod / log mask / UI mask）；本地手动 + 自动化全绿即发 **0.5.0**；真实双机 + keychain + token refresh 推到 P5-d 一起讨论。
