## 4. W2 —— `sync_changes` 裁剪

### 4.1 安全边界（四道闸）

裁剪的唯一风险点是 `isSelfReplay`：服务器 pull 按 `server_seq` 单调投递，
一旦 `pulled_seq >= 某行 server_seq`，当前游标下服务器**永远不会再投**它，
该行的 self-replay 记录就失效了 —— 这是「游标水位」的来历。但要让这句话成立，
必须先证明「表里所有已同步行的 `server_seq` 都在同一个 seq 空间」。表里没有 endpoint 列，
所以用三道结构性闸门 + 一道时间闸代替。

**闸 1 —— endpoint 单一性**：`sync_cursor` 行从不删除
（`/sync/logout-local` 保留、`clearSyncIdentity` 也不碰，`core/src/skybridge/identity.ts:51-63`），
因此「`sync_cursor` 恰好一行且 endpoint == 当前 `session.serverUrl`」
⇒ 这个库从没经由**别的 URL** 同步过。不成立（0 行 / 多行 / 不匹配）→ 整轮跳过。

**闸 2 —— 正向 provenance 水位**（v4 新增，闸 1 单独不够）：

闸 1 只能证明「URL 没变过」，证明不了「同一个 URL 背后是同一个 change log」。
反例真实存在：0.5.x / 0.6.1 **已经允许**含同步痕迹的 local 库被 claim
（`sync-auth-transport.ts:70-73` 只提示不阻断），这样的库升级到 0.6.2 后没有任何标记，
若新旧账号恰好在同一台服务器上，闸 1 会放行，而两个账号的 change log 是**各自独立的 seq 空间**。
⇒ 「没有 blocked 标记 = 安全」这个**否定式判据不成立**，必须换成正向的：

```
local_metadata.sync_retention_safe_after_local_seq = N
```

> `local_seq > N` 的行 = **0.6.2 之后、在当前 endpoint 下产生**，provenance 已知，可裁；
> `local_seq <= N` 的行 = 来历未知，**永久保留**。

写入规则（`ensureRetentionWatermark(sqlite)`，键不存在时才写）：

| 时机 | N |
|---|---|
| `installSkybridgeSession` 成功后（与 `persistSkybridgeIds` 同处，`session.ts`） | 该库**有** `sync_cursor` 行 → `max(local_seq)`；**没有**（全新 profile 库，从没同步过）→ `0` |
| 裁剪时发现键仍不存在（0.6.2 之前建的库，兜底） | 同上规则写入，且**本轮返回 `watermark_initialized`，不删任何行** |

代价：升级到 0.6.2 之前积累的行**永久保留**。可接受 —— 存量体积本来就不大，
而 0.6.2 之后的增长才是 C2 要解决的问题。将来若需要清掉这批，另开一个「确认单 endpoint
后重置 N」的显式维护动作，不在本轮。

**闸 3 —— 游标水位**：`server_seq <= 当前 endpoint 的 pulled_seq`。

**闸 4 —— 时间窗**：`synced_at < now - 7 天`。给人工排障和「刚同步完就换 endpoint」留余量。

⚠️ **仍然存在、且接受的残留**：裁剪跑过之后再发生 endpoint 归零重拉，被裁行会以「远端变更」
身份回来，`isSelfReplay` 不再认得，只能靠三元组 LWW 兜底（`update`/`trash` 相等或更旧 → skip；
`create` 对本地已删笔记短暂复活，同序列里更大 seq 的 `delete` 会再删掉 → 收敛）。
**不丢数据，会重放一次。**

📌 **给 A1（TLS）的实操建议**（带前提）：换 https 时直接迁移游标行
`UPDATE sync_cursor SET endpoint='https://…' WHERE endpoint='http://…'`，游标不归零、闸 1 继续成立。
**前提全部满足才可以做**：① https 地址指向**同一台** skybridge 实例、同一 workspace、同一 change log；
② 目标 endpoint 行**尚不存在**；③ 停 daemon + 备份 db + 在事务里执行。写进 A1 执行清单。

### 4.2 实现

**新增 `packages/core/src/sync/retention.ts`**

```ts
export interface PruneOptions {
  endpoint: string;      // 当前 session.serverUrl，与 runSync 用的同一个字符串
  retentionMs: number;
  maxRows: number;
  nowMs?: () => number;
}
export type PruneResult =
  | { pruned: true; deleted: number; cutoff: number; pulledSeq: number; safeAfter: number }
  | { pruned: false; reason: 'no_cursor' | 'multi_endpoint' | 'endpoint_mismatch'
                          | 'watermark_initialized' };

export function pruneSyncedChanges(sqlite, opts: PruneOptions): PruneResult;
export function ensureRetentionWatermark(sqlite): number;   // 幂等，返回 N
```

1. `ensureRetentionWatermark` —— 键不存在则按 §4.1 闸 2 的表写入；本轮若是刚写入的，
   直接返回 `watermark_initialized`（不删）。
2. 闸 1：读 `sync_cursor` 全部行 → 0 行 `no_cursor` / >1 行 `multi_endpoint` /
   唯一行 endpoint ≠ `opts.endpoint` → `endpoint_mismatch`。
3. 都通过才删：
   ```sql
   DELETE FROM sync_changes WHERE local_seq IN (
     SELECT local_seq FROM sync_changes
      WHERE local_seq >  :safeAfter        -- ② provenance 水位
        AND synced_at IS NOT NULL          -- ① pending 永不删
        AND synced_at <  :cutoff           -- ④ 时间窗
        AND server_seq IS NOT NULL         -- 没有 seq 就无法证明不会再投
        AND server_seq <= :pulledSeq       -- ③ 游标水位
      ORDER BY local_seq LIMIT :maxRows);
   ```
   `local_seq > :safeAfter` 是 rowid seek，顺带把稳态扫描的起点也抬上去了。
4. 常量 `RETENTION_MS = 7 天` / `MAX_ROWS = 5000`，**先用模块常量不开 toml 配置项** ——
   发版后的长期测试就是用来验这个默认值的。
5. **不做 VACUUM**（SQLite 复用释放页；真要缩文件得建库时 `auto_vacuum=incremental`）。
6. **从 `core/src/index.ts` 导出**（`// Sync (P4 Phase 2 — local change log)` 那一段旁，约 `:136`）
   —— 不导出 daemon 用不了。

**接入点：daemon**

`attemptSyncRound`（`manual.ts:219`）里 `runSync` 成功后调用，节流**至少 1 小时**：

- 节流表 `WeakMap<AppContext, number>`。⚠️ profile switch 是**原地改同一个 `AppContext`**
  （`status-broadcaster.ts:44-49`），所以这张表实际是**进程级**；在 switch teardown 里清一次
  （与 `evictSyncStatusBroadcaster` 同处，一行），「每库每小时」的语义才成立。
- **时间戳写在 `finally`** —— 否则裁剪抛错时每一轮同步都会重试。
- 裁剪抛错**只 warn，不影响同步结果**。

**日志**：`deleted > 0` → info `{kind:'sync-retention', deleted, cutoff, pulled_seq, safe_after}`；
`pruned:false` → **每进程每 reason 只 warn 一次**。写进 CLAUDE.md 的 debug 关键字列表。

### 4.3 不变量（写进 `retention.ts` 头注释 + 0011 头注释）

> `sync_changes` 自 0.6.2 起会被裁剪。**今后任何迁移都不得用「某实体在 sync_changes 里有没有
> 历史行」做判断**（0008 那种存在性 backfill）。需要类似语义时改用业务表字段或 `local_metadata` 标记。

### 4.4 D9 —— 含同步痕迹的 local 库要不要禁止 claim merge（待点头）

审阅中发现的**既有 bug，与裁剪无关但同源**：claim 整库复制会把旧 `sync_cursor` 与旧
`synced_at` 行一起带进新账号，于是

- 旧 cursor 过高 → 新账号下的 pull 会**跳过 seq 低于它的远端变更**（多设备时真丢更新）；
- 旧行 `synced_at != null` → 这些笔记**永远不会上传到新账号**（本地有、云端无）。

`isAccountEmpty` 只保证账号当前为空，挡不住这两条。

- **建议（推荐）：`hasSyncTraces === true` 时在 claim 提示里禁用「合并」，只留「保持独立」。**
  改动集中在 `claim-prompt.ts` + `maybeClaimLocalInto`（`sync-auth-transport.ts:63-73`），几行。
  完整修法（归零 cursor + 按当前业务表重建 outbox）范围明显更大，记进 backlog 另开。
- 若**不**采纳：claim 时必须把 `sync_retention_blocked` 标记与整库复制**原子化** ——
  `backupDatabase` 直接生成目标文件（`db/backup.ts:21`），复制成功但标记写失败的话，
  下次登录会走「回访」路径，标记永远补不上。做法：backup 到临时文件 → 写标记 → fsync/close →
  `rename` 到正式路径。
- **无论选哪个，W2 都不阻塞**：闸 2 的正向水位对存量库已经生效。

### 4.5 测试

- 四种 `pruned:false` 分支各自 **0 行被删**（含首次写水位的 `watermark_initialized`）。
- 水位：`local_seq <= N` 的行永不删；`> N` 且满足其余条件的行删。
- `ensureRetentionWatermark` 幂等；有 cursor 行 → `max(local_seq)`；无 → 0。
- pending 行永不删（哪怕早于 cutoff）；`server_seq > pulled_seq` 的行不删。
- 正常路径：`maxRows` 生效且按 `local_seq` 从旧到新。
- 裁剪后 `isSelfReplay` 对**仍在窗口内**的 cid 依然为 true（回归保护）。
- **性能不进普通单测**（v4 修正）：单测只断言功能（分支、行数、顺序）。
  另放一个 benchmark（`*.bench.ts` 或 `OWL_PERF=1` 才跑的用例）打印耗时，不做硬时钟断言 ——
  200k 行稳态实测 34ms 记在注释里作为基线。**本轮明确不加索引。**
- daemon：节流生效、**抛错后节流仍推进**、switch 后节流被清。

## 5. W3 —— 桌面 token 过期自愈

> 骨架沿用 `docs/plans/2026-07-24-problem-a-auto-sync-plan.md` §6 Phase 2A，
> **v2 推翻「状态 + 命令拆开」**（§5.1），**v3/v4 补齐状态机漏洞**（§5.2–§5.8）。

### 5.1 单通路：状态即命令

不新增 `sync:auth_required` 事件。理由链：reason 必须进持久快照 → 初始快照也必须能是
`auth_required`（否则 daemon 单独重启时没有生产者，§5.4）→ 这两条成立后，瞬时命令携带的信息
**严格少于** `sync:status_changed`（后者同点广播、可 GET 重查、renderer 冷启动也拿得到）。
前提是 §5.6 的统一提交点。

### 5.2 谁是「账号 profile」

`clearSkybridgeAuth()` **只清凭据**，profile / device / workspace / server_id 都留着
（`config.ts:485`）。所以「没有恢复凭据」≠「纯本地模式」：

> **要不要显示「需登录」** 由 profile 身份决定；**能不能自动恢复** 才由 capability 决定。

`AppContext` 上没有 profile id，`switchProfile` 只吃 db path。判据用**daemon 实际打开的是哪个库**
+ **这个库有没有绑过账号**：

```
isAccountProfile(ctx):
  cloud → ctx.credentialStore?.get() != null || ctx.skybridgeSession != null
  local → isRealPath(ctx.sqlite.name)
          && resolve(ctx.sqlite.name) !== resolve(paths.localProfileDbPath())
          && local_metadata 里有 skybridge_workspace_id
```

- 不读 toml：`active_profile` 在 switch 窗口内可能与 daemon 实际打开的库不一致。
- ⚠️ **`ctx.sqlite.name` 对内存库是 `':memory:'`，不是空字符串**（v4 修正）。
  `isRealPath` = 绝对路径且不等于 `':memory:'`；非真实路径一律判为**非账号**。
- 第二个条件挡住两类误报：① local 路径上的遗留账号库（被路径条件排除）；
  ② daemon 单测的临时库（没有 skybridge identity 行 → 非账号 → 初始态仍 `idle`，
  **存量测试不受影响**）。

### 5.3 `auth_reason` 三值 + 优先级

| reason | 含义 | 能自动恢复吗 |
|---|---|---|
| `missing_session` | daemon 没装 session（冷启动 / 单独重启 / switch 后） | 能：重装已存 access token |
| `token_rejected` | 真的收到 401 | 能：**必须 refresh** |
| `credentials_missing` | 账号 profile 但凭据已清（refresh 死亡后） | **不能**，终态 |

**优先级 `credentials_missing (3) > token_rejected (2) > missing_session (1)`**：
`markAuthRequired` 只允许同级或更高覆盖，同值不重复 emit（去重下沉到 broadcaster）。

⚠️ 不做优先级会有真实死循环：token 被拒后 session 已空，用户点一次「手动同步」→
`ensureSkybridgeSession` 抛 `SkybridgeAuthRequiredError` → 若降级成 `missing_session` →
renderer 重装**同一枚已被拒的 token** → 401 → 循环。

**重置点**：`markSessionInstalled()`、`markSuccess()`、broadcaster evict（profile switch）。

### 5.4 daemon —— 状态

1. **`SyncState` 加 `'auth_required'`**（两处同步改）；导出 `SYNC_STATES` 常量数组，
   把 renderer 的硬编码四值校验（`events-subscriber-core.ts:137`）改成查表。
2. **`SyncStatusSnapshot` 加 `auth_reason: AuthReason | null`**（两处同步改）。
3. **`status-broadcaster.ts`**：
   - `markAuthRequired(reason, message)`：按 §5.3 优先级 + 去重。
   - `markSessionInstalled()`：→ `idle` + `auth_reason: null` + emit。
   - **粘性规则**：
     | 方法 | 处于 `auth_required` 时 |
     |---|---|
     | `markError` / `markOffline` | **不降级**，只更新 `last_error` |
     | `markSyncing` | **`ctx.skybridgeSession == null` 时不改变状态**；有 session（真·重试）才翻 `syncing` |
     | `markSuccess` / `markSessionInstalled` | 清除（→ `idle`，reason 置空，优先级重置） |
   - **`initialSnapshot`（`:105`）四分支**：
     | 条件 | 初始 state |
     |---|---|
     | `ctx.skybridgeSession != null` | `idle` |
     | 非账号 profile（§5.2） | `idle` |
     | 账号 profile + capability 任一为真 | `auth_required` / `missing_session` |
     | 账号 profile + capability 全假 | `auth_required` / `credentials_missing` |
     ⚠️ 这只在 broadcaster **创建/evict** 时求值（`:29-52`），**不是**持续生效的规则 ——
     运行期由 GUI main 经 §5.7 的端点显式收敛。
4. **新增 `daemon/src/sync/auth-signal.ts`**：
   ```
   signalAuthRequired(ctx, reason, message):
     if (!isAccountProfile(ctx)) { broadcaster.markError(message); return }
     broadcaster.markAuthRequired(reason, message)
   ```
   ⚠️ 非账号 profile **不能什么都不做** —— 手动同步已 `markSyncing`，直接 return 会把状态
   永久卡在「同步中」。
5. **调用点**：`manual.ts:283-288` 的 catch（401 → `token_rejected`；
   `SkybridgeAuthRequiredError` → `missing_session`），invalidate 后调 `signalAuthRequired`，
   **不再调 `markError`**；`/sync/devices`、`/sync/revoke-device`（`routes/sync.ts:100`、`:133`）同理。
6. **`/sync/session` 两个方向都要收敛**：
   - 成功 → evict broadcaster **并显式广播一次 idle**（`routes/sync.ts:207` 之后）；
     现在只 evict 不广播，renderer 会永远卡在 `auth_required`。
   - **失败 → `markAuthRequired('missing_session', …)`**（v4 新增）：路由在 install 之前
     已经 `stopBackgroundHandles` + `ctx.skybridgeSession = null`（`:201-202`），
     install 再抛出的话，快照仍停在旧的 `idle` —— 与实际（无 session）不符。

### 5.5 SSE 的 401 必须进状态机

`sse-bridge.ts:197-205` 的 `onError` 只 `markOffline` + 重连。后果：subscribe 阶段就 401 →
`onOpen` 永不触发 → `onOpen` 里的 catch-up sync 跑不到 → 没有任何 REST 轮次 →
永远停在「离线」+ 无限重连一枚死 token（`interval_min <= 0` 时连 scheduler 兜底都没有）。

**改法**：`onError` / subscribe-catch 判 401（`isApiError(err) && err.status === 401`，
用 0.6.1 抽出的 `sync/skybridge-errors.ts`）→ `invalidateSkybridgeSession` +
`signalAuthRequired(ctx, 'token_rejected', …)` + **停止重连**；由 `/sync/session` 成功后的
`ensureBackgroundHandles` 重新拉起 bridge（已有逻辑）。非 401 维持现状。

### 5.6 renderer —— 唯一提交点

当前三条写 store 的路径**互相绕开**：`setSnapshot`（SSE）、`fetch()` 里的 `applyNow`
（GET，`stores/sync-status.ts:135`）、deferred timer 的直接 `set`（`:120-128`）。
「冷启动 GET 读到 `auth_required`」这条最关键的路径根本不经过检测点。

收敛成一个 `commitSnapshot(next)`，三条路径共同调用：

1. 校验不变量：`state === 'auth_required'` ⇒ `auth_reason != null`；其余 state ⇒ `auth_reason == null`
   （违反则 warn + 丢弃，与现有 malformed 处理一致）。
2. 写 store。
3. 检测「进入 `auth_required`」（含 `null → auth_required`）→ 调
   `getPlatform().sync.requestRecovery?.(auth_reason)`。
   `credentials_missing` **不调**（终态）；停留同一态不重复触发。
4. `fetch()` 里那段 `state:'idle'` 的伪造删掉，改用返回的 `state` / `auth_reason`。

**（D3）`GET /sync/status`** 返回 `{...readSyncStatus(ctx), state, auth_reason, last_error}` ——
计数仍走实时查询（broadcaster 缓存的 `pending_count` 只在 markSuccess 时重算）。
`shared/src/types.ts:168` 的 `SyncStatusResult` 补三个字段。

**`SyncStatusBar`**：`STATE_INFO` 补 `auth_required: { label: '需登录', dotClass: 'bg-red-500' }`；
popover 文案按 reason 分：`credentials_missing` →「登录已失效，请在 设置 → 同步 重新登录」（带链接）；
其余 →「正在自动恢复登录…」。`isAccountSnapshot`（`:262`）已把纯本地工作区挡在外面。

**preload / IPC**：`sync.requestRecovery(reason)` → `ipcRenderer.invoke('sync:request-recovery', reason)`；
`platform/types.ts` 可选成员（web 不实现）；`sync-ipc.ts` 注册 handler。

### 5.7 D5 —— 删掉 `/sync/logout-local`，换 `POST /sync/auth-unrecoverable`

`/sync/logout-local` **删除**：它不写 toml、不清凭据（daemon 不写 toml），无生产调用方
（GUI logout 走 `/sync/switch local`），且在新状态机下会造出「清 session → 快照 `missing_session`
→ renderer 把 toml 里还在的旧 token 装回去 = 撤销登出」的矛盾路径。同步删掉
`routes/system.ts:74` 的清单项与相关测试。

**新增 `POST /sync/auth-unrecoverable`**（local only，`cloudForbidden`）—— 解决 v3 遗留的
「refresh 死亡后状态不收敛」：broadcaster 缓存在 WeakMap，`initialSnapshot` 只在创建/evict 时
求值（`status-broadcaster.ts:29-52`），而 GUI main 清 toml 凭据**不会**通知 daemon
（无文件监听）。于是状态会一直停在 `auth_required / token_rejected`，UI 显示
「正在自动恢复登录…」而不是「请重新登录」。

该端点只做四件事：`stopBackgroundHandles` → `ctx.skybridgeSession = null` →
`markAuthRequired('credentials_missing')` → **保留 db identity 与 `sync_cursor`**（不 `clearSyncIdentity`）。
GUI main 在 `clearSkybridgeAuth()` 之后调用（`recoverImpl` 的 `dead` 分支、
`restoreSessionOnStartupImpl` 的 dead-refresh 分支 `sync-auth.ts:599`）。best-effort：
daemon 不在也不算失败。

不违背 D4：瞬时 HTTP 只是**状态更新入口**，最终真相仍是可查询的持久快照。

### 5.8 GUI main —— 新模块 `sync-auth-recovery.ts`

1. **分层（原写法会死锁）**：`runSwitchExclusive` 显式非重入（`sync-switch-queue.ts:15-17`），
   而 `refreshSession()` 自己已在队列里（`sync-auth-renewal.ts:56`）。**只有最外层持锁**：
   ```
   sync-auth-renewal.ts:
     refreshSessionUnlocked(): Promise<RefreshResult>       ← 不进队列
     refreshSession() = runSwitchExclusive(refreshSessionUnlocked)
   sync-auth-recovery.ts:
     reinstallFromConfigUnlocked(): Promise<InstallResult>  ← 不进队列
     requestRecovery(reason)   ← 外部入口（renderer / focus / resume），受 10s 限流
     runRecoveryAttempt(reason, gen)  ← 内部入口（退避 timer），**不受 10s 限流**
   ```
   同步更新 `sync-switch-queue.ts:16` 的「六个 wrapped 入口」注释。
2. **两个入口必须分开**（v4 修正）：退避从 2s / 5s 起步，若内部 timer 回头调受 10s 限流的
   同一个函数，重试会被**静默吞掉**，而 timer 又不会再排 —— 恢复链**永久停止**。
   内部入口不过限流（或按剩余限流时间重新排期）。
3. **generation 不只保护 timer**（v4 修正）：`recoverSession` 必须**进队列前捕获 generation、
   拿到锁后再比一次**。否则：A 发出 `token_rejected` → 用户切到 B（切换先拿到队列）→
   A 的 recovery 在队列里等 → 切换完成后它读到的是 **B 的配置**，去刷新了 B。
   generation `++` 时同时**重置该代的 singleflight 与限流时间戳**。
   落点 = 现有每处 `clearRefreshTimer()` 旁边（`sync-auth.ts:181`、`:286`、`:354`、`:525`）。
4. **refresh 五态**（v4 补第五种）：
   `{outcome: 'refreshed' | 'refreshed_not_installed' | 'dead' | 'transient' | 'no_credentials'}`
   - `refreshed_not_installed` 语义：**轮换后的凭据已落盘、renewal timer 已排好**，
     只是 `postSyncSession` 失败。recovery 模块拿**新的** access token 进入 reinstall 退避，
     **不向 timer 回调抛未处理异常**。
   - 现实现把 dead / transient 一律 `catch` 后 `return`（`sync-auth-renewal.ts:77-84`），
     外层执行不了「dead → `clearSkybridgeAuth()`」。
5. **reason 分派**：
   - `missing_session` → `reinstallFromConfigUnlocked()`：解密已存 `encrypted_token` 重发
     `/sync/session`，**不做 refresh**（手上那枚 access 本来就是好的，失败的只是「发给 daemon」
     这一步）。装上去若其实已死，下一轮 401 → `token_rejected`，自洽。
   - `token_rejected` → `refreshSessionUnlocked()`；`dead` → `clearRefreshTimer()` +
     `clearRecoveryTimers()` + `clearSkybridgeAuth()` + **调 `/sync/auth-unrecoverable`**（§5.7）。
   - `credentials_missing` → no-op + 日志（renderer 也不会发，双保险）。
6. **退避 timer 生命周期**：reinstall 独立退避 `[2,5,10,30,60]s`，且
   **不在队列里 sleep**（退避用队列外 `setTimeout`，队列里只放「一次 refresh/install」的临界区，
   否则整个退避梯度会把 profile 切换堵死）、**generation 可取消**、一律 `unref()`。
7. **修 `refreshSessionImpl` 顺序**（`sync-auth-renewal.ts:86-95`）：
   `refresh → persistRotated → scheduleRefresh(expiresAt)`（**先排下一次**）→ 再 `postSyncSession`；
   install 失败返回 `refreshed_not_installed`，**不吃掉 renewal timer、不产生 unhandled rejection**。
8. **（D8）renewal margin clamp —— 两套实现都改**：
   ```
   ttl       = max(0, expiresAt - now)
   lead      = min(60s, ttl / 2)
   refreshAt = expiresAt - lead
   delay     = max(1s, refreshAt - now)
   ```
   - 桌面 `sync-auth-renewal.ts:118-125`：现在固定减 60s、下限 1s ⇒ TTL≤60s 每秒 refresh。
   - 云端 `cloud-login.ts:512`：`Math.max(0, …)` **下限是 0** ⇒ TTL<60s 是真正的紧循环。
   - `maybeRefreshNow`（`:103-107`）必须用**同一个 `refreshAt`**，否则 timer 修好了、
     窗口聚焦时仍按固定 60s 提前量刷新。把 `refreshAt` 与 `currentExpiresAt` 一起存成模块状态。
9. **resume / focus 兜底**：`index.ts:236-243` 现有 `maybeRefreshNow()` 旁边加一次
   `GET /sync/status`，读到可恢复的 `auth_required` 就 `requestRecovery(reason)` ——
   覆盖「窗口全关、没有 renderer 转发」的场景。

### 5.9 怎么测

❌ **调小 `access_ttl_sec` 测不出来**：客户端提前 60s 刷新、最小延迟 1s，TTL=60s 变成每秒
refresh 风暴，token 永远不会自然过期。**proactive timer 的设计目的就是让 token 不过期** ——
真机要测的从来不是「等它过期」，而是「access 被拒但 refresh 仍有效」。

✅ **`token_rejected`（REST）**：测试服务器上跑
```sql
UPDATE auth_tokens SET expires_at = 1 WHERE device_id = '<桌面 device id>';
```
→ 服务端 `TOKEN_EXPIRED` → **HTTP 401**（`…/auth/plugin.js:42-45`、`:60-66`），refresh_tokens 不受影响。
⚠️ **注入不会断开已建立的 SSE**，必须主动制造一次 REST 轮次：改一条笔记（push-on-mutation
≤2s 发起）或点「手动同步」。

✅ **`token_rejected`（SSE，§5.5 回归）**：注入后重启 skybridge server 强制 SSE 重连 →
subscribe 阶段 401 → 断言状态变「需登录」而不是无限「离线」。

✅ **`missing_session`**：GUI 保持开着，单独重启 daemon（`just stop-daemon && just dev-daemon`）。

✅ **`credentials_missing`**：服务端 device-revoke（refresh 家族一起失效）→ 断言状态
**立刻**变「请重新登录」（靠 §5.7 的端点，不是等下次重启）；再重启 daemon，断言仍是「需登录」
而不是掉回「已同步」。

单元测试用 fake timers + 注入 transport，不依赖真服务器。

### 5.10 验收

- 注入 access 失效 + 一次编辑 → **无需任何手动操作**，状态栏最多闪一下「需登录」就回「已同步」。
- daemon 单独重启后 GUI 自动重装 session。
- SSE subscribe 401 → 「需登录」，不再无限重连死 token。
- device-revoke → **立刻**「请重新登录」，凭据已清，重启 daemon 后仍是「需登录」，无重装死循环。
- 手动同步在任何分支下都不会把状态卡在「同步中」。
- 切 profile 期间/之后不产生脏恢复（排队中的恢复请求成为 no-op）。

### 5.11 测试清单

- **daemon**：粘性规则四组合；reason 优先级（弱不覆盖强、同值不 emit、三个重置点）；
  `initialSnapshot` 四分支；`isAccountProfile` 的两类误报 + `':memory:'` 判为非账号；
  `signalAuthRequired` 在非账号 profile 上落 `markError`（**不能留在 syncing**）；
  SSE 401 → invalidate + `token_rejected` + 停重连；`/sync/session` 成功广播 idle、
  **失败落 `missing_session`**；`/sync/auth-unrecoverable` 的四个效果 + cloud 404；

  停留不重复触发、`credentials_missing` 不触发；`SyncStatusBar` 按 reason 分文案。

  - **2s 退避重试不被 10s 外部限流吃掉**（v4 新增）；
  - **A 的 recovery 排队期间切到 B → 恢复成为 no-op**（v4 新增）；
  - 队列不重入（recoverSession 与 refreshSession 并发不死锁）；
