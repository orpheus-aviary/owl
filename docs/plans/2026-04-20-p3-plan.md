## 2. 核心架构决策（P2 讨论落定）

### 2.1 CLI 与 GUI 对等独立

- CLI 通过 `npm i -g @orpheus-aviary/owl-cli` 单独安装
- GUI 通过 GitHub Releases 下载 installer
- 两者**互不拉起**
- **0.3.0 明确 GUI installer 不内置 CLI**；"Docker Desktop 式 installer 把 `owl` 复制到 PATH" 是 post-P3 候选（见 §10），此处不是 P3 架构承诺

### 2.2 Daemon 归属

- GUI 启动时自动 spawn daemon（已有行为）
- CLI **永不自动拉 daemon**
  - GUI 在跑 → CLI 走 HTTP
  - GUI 未跑 → CLI 直连 SQLite（WAL 模式短事务）
- WAL 允许并发读 + 单写，SQLITE_BUSY 时 CLI 指数退避重试 3 次

### 2.3 没有"CLI 下载 GUI"命令

- npm 不分发 200MB 二进制
- `owl doctor` 检测环境，打印 GitHub Releases URL 供用户手动下载

### 2.4 版本命名

| 阶段完成点 | 版本 | 语义 |
|---|---|---|
| P2 完成（GUI 基础功能） | `0.2.0` | 首个有 release 的 milestone |
| P3 完成（CLI + GUI 全套） | `0.3.0` | 外部调用可用 |
| P4 完成（同步稳定） | `1.0.0` | API 契约稳定 |

用 `0.x` 起步的理由：P3 / P4 还会引入显著变动（CLI 新增公共面、P4 schema 改动），`0.x` 的 minor bump 允许 breaking，不消耗 major。

### 2.5 npm scope

- 组织名：`@orpheus-aviary`（用户需在 npm 申请免费组织）
- 命名格式：`@orpheus-aviary/<project>-<variant>`
- **P3 只 rename 对外发布的包**：`@owl/cli` → `@orpheus-aviary/owl-cli`
- **内部 workspace 包保持 `@owl/*`**：`@owl/core`、`@owl/daemon`、`@owl/gui` 不改名
  - 理由：内部名字不暴露给用户；全量 rename 会把大量机械改动混进 P3 关键路径
  - 未来若需要公开 core，再 rename 成本低
- `@owl/core` **不发布**，通过 bundling 合并进 CLI（见 §5.3）
- 未来 `@orpheus-aviary/lark-cli`、`@orpheus-aviary/jay-cli` 等无缝扩展

### 2.6 打包不签名

- macOS：不上 Apple Developer（$99/年），用户右键 → 打开绕过 Gatekeeper
- Windows：不买 code signing 证书（$100-400/年），用户点 "仍要运行" 绕过 SmartScreen
- Linux AppImage：天然不需要签名
- 等有真实用户量抱怨再补签名

4. **agent-loop**：累积流式 `thinking_delta` 到本轮 assistant message；保留 signature
5. **conversations**：在 LlmMessage 上持久化 thinking 文本与 signature
6. **daemon SSE**：把 `thinking_delta` 透传给 GUI（沿用现有 `dispatcher` 事件契约）
7. **GUI**：

### 5.2 智能切换

```typescript
const daemonAlive = await detectDaemon();  // HTTP /status, 200ms timeout
const mode = daemonAlive ? 'http' : 'direct';
```

- `http` 模式：所有命令走 `fetch` 到 `http://localhost:<daemon.port>`；端口从 `owl_config.toml` 的 `daemon.port` 读取，默认 `47010`（见 `packages/core/src/config/index.ts:111`）。**禁止硬编码 `8080` 或任何其他数字字面量**
- `direct` 模式：直接 `createDatabase()`（来自 `@owl/core`），执行完关闭
- 环境感知：`http` 模式暴露 `open` 等需要 GUI 的命令；`direct` 模式隐藏
- `detectDaemon()` 同样用配置 `daemon.port`，不是猜端口

### 5.3 打包与发布（决定：tsup bundle + npm i -g）

**0.3.0 分发方式定死 `npm i -g @orpheus-aviary/owl-cli`**。单二进制（`pkg`）推迟到 post-P3（见 §10）。

**关键问题**：CLI 当前依赖 `@owl/core`（`workspace:*`、`private`），直接 `npm publish` 会爆。采用 **选项 B：bundle core 业务逻辑、external native modules、发布时输出干净 manifest**。

**实施步骤**：

1. 引入 `tsup` 作为 CLI 构建工具（esbuild 内核，零配置 ESM + d.ts）
2. `apps/cli/tsup.config.ts`：
   - `entry: ['src/index.ts']`
   - `format: ['esm']`（Node 20+ 原生支持）
   - `bundle: true`、`noExternal: ['@owl/core']` — 把 core 业务逻辑打进 CLI 产物
   - `external: ['better-sqlite3']` — native，必须运行时解析
   - `external: ['drizzle-orm', 'commander', 'pino', 'pino-roll', 'uuid', 'smol-toml']` — 纯 JS，也外置，保持体积小和版本透明
3. **生成 publishable manifest**（与 workspace 的 `package.json` 不同）：
   - `name: "@orpheus-aviary/owl-cli"`、`private: false`
   - 移除 `@owl/core` 的 `workspace:*` 依赖
   - `dependencies` 列出所有 external：`better-sqlite3`、`drizzle-orm`、`commander`、`pino`、`pino-roll`、`uuid`、`smol-toml`
   - `bin: { "owl": "dist/index.js" }`（bin 名从 `owl-cli` 改为 `owl`）
   - 实现：prepack 脚本生成 `dist/package.json`，`pnpm publish` 指向 `dist/`；或用 `clean-publish`
4. CI 发布：
   ```bash
   pnpm --filter @owl/cli build
   pnpm --filter @owl/cli publish --access public --no-git-checks
   ```

**native module UX 风险**：

- `better-sqlite3` 对主流 Node LTS 有 prebuilt binary；非 LTS / musl / 非主流架构会落到本地编译（需要 python + make + C toolchain）
- `owl doctor` 必须检测 Node 版本 + `better-sqlite3` 能否加载，给明确错误提示和引导

### 5.4 `open_note_in_gui` 反向通道

CLI 在 http 模式想让 GUI 打开指定笔记 tab，需要 daemon → GUI 推送。

**方案对比**：

| 方案 | 复杂度 | 优点 | 缺点 |
|---|---|---|---|
| WebSocket (`@fastify/websocket`) | 中 | 全双工，未来扩展性好 | 多一个协议 |
| Server-Sent Events（已有） | 低 | AI 已用 SSE，复用基础设施 | 单向（daemon → GUI） |
| 轮询 `/events?since=<cursor>` | 低 | 无状态 | 延迟高 |

**推荐 SSE**：已有 `initSse` 基础设施，GUI 侧加一个全局事件订阅组件。路由 `/events`：
- 推送事件类型：`open_note`、未来扩展 `config_changed`、`note_applied_external` 等
- GUI mount 时订阅，收到 `open_note { id }` 调 `openNoteById(id) + navigate('/')`

### 5.5 Schema migration 系统（决定：rebuild + backup，user_version 单一 truth source）

**核心决策**：0.3.0 对老库采取"rebuild + 备份 + 不兼容旧架构"策略，避免 baseline 检测的复杂度和 DDL / ALTER / runner 三套并存的维护负担。

**目录结构**：

```
packages/core/src/db/migrations/
├── 0001_initial.sql   # = 今天完整 DDL（含 auto_delete_at、FTS 虚表、触发器）
├── 0002_*.sql         # 未来 schema 变更
└── ...
```

**单一 truth source = `PRAGMA user_version`**。不引入 `schema_version` 表。

**Runner 逻辑（启动时）**：

代码里维护一个常量 `LATEST_KNOWN_VERSION`（0.3.0 = 1，未来版本 bump）。判断顺序**必须先处理未来版本**，否则 `v >= 2` 会把未知版本误吞：

```
const LATEST = LATEST_KNOWN_VERSION;  // 0.3.0 中为 1
读 PRAGMA user_version as v:

  if v > LATEST:
    → 报错："数据库 v{v} 来自更新版本应用（本版本支持到 v{LATEST}），请升级应用"，拒绝打开

  if v == 0:
    if 库文件不存在 或 sqlite_master 无业务表:
      → 新库：跑 0001_initial.sql，设 user_version = LATEST（= 1）
    else:
      → 老库（0.2 或更早）：走一次性 rebuild 分支（见下）
    return

  if v == LATEST:
    → 正常启动（0.3.0 下 v == 1）
    return

  if v < LATEST:
    → 按顺序 apply version v+1 ... LATEST 的 migration 文件（未来版本用）
    return
```

0.3.0 里唯一会走"apply migrations 前进"的场景是**没有**的（`v == 1 == LATEST`）；该分支为未来版本预留。但代码结构先写好，避免 0.4.0 再改 runner 骨架。

**一次性 rebuild 分支**（仅 0.3.0 ship，0.4.0 可删）：

> ⚠️ WAL 模式下 `owl.db-wal` / `owl.db-shm` 是活跃 sidecar，简单 `cp owl.db ...` 会漏掉已提交但未 checkpoint 的数据。必须用 **SQLite online backup API** 或显式 checkpoint，且替换阶段必须清掉旧 sidecar。

1. **确认独占访问**：检查没有其他进程持有 `owl.db`（daemon 未起、无残留 `.owl.lock`）。有冲突 → 中止并报错
2. **打开旧库 + WAL checkpoint**：`PRAGMA wal_checkpoint(TRUNCATE)` — 把 WAL 内容合并回主文件、清空 sidecar
3. **备份**：用 better-sqlite3 的 `db.backup('owl.db.v0.2-backup-<unix-ts>')`（在线 backup API，自动处理一致性快照）
4. **新建 `owl.db.new`**（独立路径），跑 `0001_initial.sql`
5. **按表顺序从旧库 INSERT 到新库**（清单见下，用事务包起来）
6. **重建 FTS**：`INSERT INTO notes_fts(notes_fts) VALUES('rebuild')`
7. **新库 `PRAGMA user_version = 1`**，关闭新库连接（确保 WAL flush）
8. **关闭旧库连接**
9. **Sidecar 清理 + 原子替换（带回滚）**：
   ```
   try:
     a. fs.renameSync('owl.db', 'owl.db.old-pre-v0.3')
     b. try fs.unlinkSync('owl.db-wal'); try fs.unlinkSync('owl.db-shm')  // ENOENT 忽略
     c. fs.renameSync('owl.db.new', 'owl.db')
   catch err:
     // 回滚：把原库放回原位
     if exists('owl.db.old-pre-v0.3') and not exists('owl.db'):
       fs.renameSync('owl.db.old-pre-v0.3', 'owl.db')
     throw err
   ```
   - 步骤 2 已经 `wal_checkpoint(TRUNCATE)`，主文件自包含；删掉 `-wal`/`-shm` 不会丢数据，SQLite 下次打开自行重建
   - 回滚后原路径恢复原库；`.new` 和 `.backup` 留在盘上供 debug

10. **失败恢复契约（精确版）**：
    - **步骤 1-8 任一失败**：原库路径 `owl.db` 原样不动；`.new` / `.backup` 可能部分存在，清理后重试
    - **步骤 9c 失败**：try/catch 自动回滚，最终原路径仍指向可用原库
    - **进程被 `kill -9` 或断电发生在步骤 9a 与 9c 之间**（极小窗口，非应用层错误）：原路径可能不存在，但数据仍在 `owl.db.old-pre-v0.3` 和 `owl.db.v0.2-backup-<ts>`；启动时应检测"`owl.db` 不存在但 `.old-pre-v0.3` 存在"这种残局，log 指引用户手动 rename 回（或未来 `owl doctor --recover` 自动处理）
    - **任何情况下**：`owl.db.v0.2-backup-<ts>` 始终是步骤 3 的一致快照，是最后保险

**数据迁移表清单（COPY）**：

- `folders`、`notes`（含 `auto_delete_at`）、`tags`、`note_tags`、`reminder_status`、`local_metadata`
- 实施时 `grep -r "CREATE TABLE" packages/core/src/db/` 再核对一次，防漏表

**不 COPY**：

- FTS 虚表 / 其镜像表（由步骤 4 重建）
- 触发器（`0001_initial.sql` 已定义）
- `owl.sync.db`（migration 同步副本，由 migration 工具管理，应用不碰）

**UX 与启动时序（关键：当前 GUI 在窗口创建前就 spawn daemon、daemon 启动即打开库）**

当前 `packages/gui/src/main/index.ts:59-71` 是 `whenReady → spawnDaemon → createWindow`，`packages/daemon/src/cli.ts:44` 启动即 `createDatabase()`。如果不动这个时序，没地方给用户弹 migration 确认框。**责任划分必须写死**：

- **GUI main process**：在 `whenReady` 内、**spawn daemon 之前**做 migration precheck
  1. 只读打开 `owl.db` → 读 `PRAGMA user_version`
  2. `v == 0` 且库非空（老库）→ 先 `createWindow`，前端加载一个专用 `MigrationDialog` 路由（不挂主 UI），等待用户确认
  3. 确认后：在 main 进程里同步跑 rebuild（better-sqlite3 同步 API，完成前**绝不 spawn daemon**）
  4. 完成后 → `spawnDaemon`，前端切到主 UI
  5. 用户取消 / rebuild 失败 → 显示错误界面 + 原库和 backup 路径，退出或重试
- **Daemon 独立启动**（无 GUI，例如 `just dev-daemon` 或用户直接跑）：启动时只读检查 `user_version`，若需要迁移 → **不调用 `createDatabase()` 的初始化路径**，log 清晰错误 + exit non-zero，提示用户启动 GUI 或跑 `owl migrate`
- **CLI `direct` 模式**：同 daemon — 检查，不自动迁移，提示用户跑 `owl migrate` 或启动 GUI
- **新增 `owl migrate` 子命令**：交互式 rebuild（TTY prompt y/N，`--yes` 跳过），供纯 CLI / 脚本场景使用

**关键不变量（按 runner 分支精确区分，不能一刀切"不是 LATEST 就抛"）**：

`createDatabase()` 内部流程：

1. 打开连接 → 读 `user_version as v`
2. **`v > LATEST_KNOWN_VERSION`** → 抛 `IncompatibleDbError`（数据库来自更新版本，应用无力处理。调用方退出 / 显示错误页）
3. **`v == 0` 且库非空（老库）** → 抛 `MigrationRequiredError`（需要用户确认的 rebuild。GUI 走 modal；daemon/CLI `direct` 打印引导后退出；CLI 可经由 `owl migrate` 进入）
4. **`0 < v < LATEST_KNOWN_VERSION`**（未来版本的常规向前迁移）→ **静默** apply 缺失的 migration 文件（纯增量 DDL / ALTER），完成后进入正常路径。**不抛 `MigrationRequiredError`**
5. **`v == LATEST_KNOWN_VERSION`** 或 **`v == 0` 且库为空**（初始化 0001）→ 正常路径

两种错误语义不同，不能合并：

| 错误 | 触发条件 | 处理方 | 可恢复性 |
|---|---|---|---|
| `MigrationRequiredError` | `v == 0` 老库（需破坏性 rebuild） | GUI modal / `owl migrate` | 用户确认后可恢复 |
| `IncompatibleDbError` | `v > LATEST`（未来库） | 退出 + 提示升级应用 | 非本版本能恢复 |

如果未来某个 migration 确实是破坏性的（例如 0.5.0 要重建某张表）、需要用户确认，再在该 migration 文件头标记 `requires_confirmation: true`，runner 读到时抛 `MigrationRequiredError`。当前（0.3.0）无此场景。

**备份命名**：`owl.db.v0.2-backup-<unix-ts>`

**失败恢复策略**：不自动还原；报错明确指出原库位置 + backup 位置，引导用户手动处理或联系。未来可考虑 `owl doctor --recover`（见 §10）。

**代码位置**：

- `packages/core/src/db/migrate.ts`（新建）：rebuild 主流程（checkpoint / backup API / copy / sidecar 清理 / 回滚）+ `MigrationRequiredError` + `IncompatibleDbError` + 未来常规前向 migration runner
- `packages/core/src/db/index.ts` 的 `createDatabase()`：打开后读 `user_version` 并按上文"关键不变量"的分支分派（`v > LATEST` 抛 `IncompatibleDbError`；`v == 0` 老库抛 `MigrationRequiredError`；`0 < v < LATEST` 静默前向迁移；其余正常）
- `packages/gui/src/main/index.ts`：`whenReady` 分支加 precheck，替换当前无条件 `spawnDaemon` 逻辑
- `packages/daemon/src/cli.ts`：启动时 catch `MigrationRequiredError`，log + exit 1
- `apps/cli/src/commands/migrate.ts`（新增）：TTY 交互 rebuild
- `createTables()` 整块 DDL 收掉，改由 `0001_initial.sql` 承担；替换当前 `migrateSchema()` 的 ad-hoc ALTER 逻辑

**一次性 vs 永久**：

- rebuild 分支代码只在 0.3.0 存在
- 0.4.0 假设所有活库 `user_version >= 1`，删除 rebuild 分支
- 用户跨版本跳跃（0.2 → 0.4+）会触发 "v=0 但代码不识别" 报错，引导先装 0.3.0 过渡

## 10. 从 P3 移出的交付项（Post-P3 / 0.4.0+ 候选）
