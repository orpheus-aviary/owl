## 1. 现象记录

> 全部来自 2026-08-11 的真机复盘。设备：桌面 `Owl.app` 0.6.2（daemon pid 68641，

### 1.1 入口：日志构成不成比例

复盘 W2 裁剪效果时顺手看了日志构成。桌面单个日志文件（`daemon.log.23`，一天，6.5 MB）：

```
20710 条  [sync] apply note … — LWW skip
 4075 条  [sync] pull skip note metadata op (no updated_at_ms)
  392 条  [sync] apply folder …
   52 条  change event（SSE）
   16 条  idle watchdog fired / connected / health-probe started|stopped
    9 条  pruned acked sync_changes rows
```

当时服务端变更日志总长约 1000 条（`pulled_seq ≈ 1000`）。**两万条 apply 对一千个 seq**，
比例明显不对。

复现命令：

```fish
grep -o '"msg":"[^"]\{0,45\}' daemon.log.23 | sed 's/[0-9a-f]\{8\}-[0-9a-f-]*/<id>/g' | sort | uniq -c | sort -rn | head
```

只有 `pull skip note metadata op` 这条日志带 `seq=`，用它切分轮次（seq 变小 = 新一轮）：

```
2026-08-10T02:30:01Z  seq 2 → 416
2026-08-10T02:37:15Z  seq 2 → 416
2026-08-10T02:37:39Z  seq 2 → 416
…
2026-08-10T06:41:39Z  seq 2 → 906
2026-08-10T06:41:47Z  seq 2 → 916
…                                    ← 一天 49 轮，无一例外从 seq 2 起
```

天花板随日志增长（416 → 906 → 916 → 928 → 949 → 996 → 1000），起点恒为 2
（seq 1 是个 folder create，不产生这条日志）。**每一轮都在重放整条变更日志。**

复现命令：

```fish
grep -h 'pull skip note metadata' daemon.log.23 | sed -E 's/.*"time":"([^"]*)".*seq=([0-9]+).*/\1 \2/' | awk '{t=$1;s=$2+0; if(NR==1||s<prev){if(NR>1)printf "%s  seq %d→%d\n",st,lo,prev; st=t;lo=s} prev=s} END{printf "%s  seq %d→%d\n",st,lo,prev}'
```

### 1.4 排除法

| 假设 | 结论 | 依据 |

| 服务端 `since` 语义有问题 | ❌ 排除 | `skybridge/packages/server/src/services/change-log.ts:178` 是 `WHERE workspace_id = ? AND server_seq > ?` |

### 1.5 决定性证据

在一次 **push-only** 的轮次之后立刻查表：

```
┌───────┬──────────────────────────┬────────────┬────────────┬─────────────────────┐
│ rowid │         endpoint         │ pulled_seq │ pushed_seq │         upd         │
├───────┼──────────────────────────┼────────────┼────────────┼─────────────────────┤
│ 1     │ http://47.99.215.39:8443 │ 0          │ 1011       │ 2026-08-11 11:36:23 │
└───────┴──────────────────────────┴────────────┴────────────┴─────────────────────┘
```

**`pulled_seq` 被清成了 0，`pushed_seq` 刚写成 1011，`updated_at` 正是那一秒。**
反过来也成立 —— 复盘全程多次看到 `pulled_seq=1002 / pushed_seq=0`（那是 pull 清掉了 push 游标）。
`GET /sync/status` 一直显示 `"pushed_seq": 0` 也是同一个 bug 的表症，之前被当成「还没实现」。

### 1.6 为什么单测没抓到

`engine.test.ts` 有两个用例：

- `:314-315` —— 只 pull 的轮次后断言 `pulled_seq = 7, pushed_seq = 0`
- `:376` —— 只 push 的轮次后断言 `pushed_seq = 42`

**两个用例各自从干净的库出发，没有任何一个测「pull 之后再 push，另一列还在不在」。**
而 `upsertSyncCursor` 的 doc comment（`engine.ts:149-151`）恰恰声称
"subsequent calls preserve the opposite column via `COALESCE(excluded.*, sync_cursor.*)`" ——
**这句断言从来没被测过，而且是错的。**

### 1.7 影响面

- **无数据损坏**：重放的变更要么被 `isSelfReplay` 跳过，要么 LWW 判定为「本地不旧」而跳过。
  复盘时查 `conflict_record` 只有 3 行，全部是 2026-07-24（0.6.1 时期）的 待办 笔记冲突、
  `resolution='ignored'`，**三周的日日重放没有产生新的误报冲突** —— 但这是运气：
  误报冲突只在「重放命中一条 pending 本地编辑」时才发生，而 `pending` 平时是 0。
- **成本**：每次本地写入 → 下一轮全量重放。今天 1000 条变更、单轮 ~1.8 秒 + 6.5 MB/天日志；
  **随变更日志线性恶化**，一年后每次改笔记都要重放几万条。笔记本电池、移动网络、云端 CPU 全在白烧。
- **和 W2 裁剪的负向交互（本轮最需要记住的一条）**：
  1. 裁剪闸 3 是 `server_seq <= pulled_seq`。**push 之后 `pulled_seq=0` ⇒ 那一轮裁剪一行都删不掉。**
     0.6.2 的裁剪效果是「被这个 bug 随机腰斩过的」结果 —— 修完 V1 之后裁剪只会更有效。
  2. `retention.ts:38-43` 写着一条「已接受的残留风险」：*游标被重置为 0 并重拉全量时，
     被裁掉的行会以「远端变更」身份回来，`isSelfReplay` 认不出，靠 LWW 三元组兜底，
     `create` 可能短暂复活一条本地已删的笔记*。**V1 让这个「理论残留」每天真实发生几十次。**
     目前没出事，是因为同一轮里 create 和后续的 delete 都会被重放、净效果抵消。但这不是设计意图。

## 2. V1 根因

`packages/core/src/sync/engine.ts:161-171`：

```sql
INSERT INTO sync_cursor (endpoint, pulled_seq, pushed_seq, updated_at)
  VALUES (?, COALESCE(?, 0), COALESCE(?, 0), ?)          -- ← 元凶在这行
ON CONFLICT(endpoint) DO UPDATE SET
  pulled_seq = COALESCE(excluded.pulled_seq, sync_cursor.pulled_seq),
  pushed_seq = COALESCE(excluded.pushed_seq, sync_cursor.pushed_seq),
  updated_at = excluded.updated_at
```

调用方 `.run(endpoint, fields.pulledSeq ?? null, fields.pushedSeq ?? null, fields.nowMs)`。

schema 是 `pulled_seq INTEGER NOT NULL DEFAULT 0`，直接插 NULL 会违反约束，
所以 VALUES 里加了 `COALESCE(?, 0)` 兜底 —— **但这个 COALESCE 把 NULL 变成 0 的时机
早于 `excluded` 的生成**。于是 DO UPDATE 分支里 `excluded.pulled_seq` 是 **0 而不是 NULL**，
`COALESCE(0, sync_cursor.pulled_seq)` 返回 **0**，把老值冲掉。

两个 COALESCE 的意图互相打架：一个为了满足 NOT NULL，一个为了「不传就保留」，
后者依赖前者没干过的事。

**最小复现**（`sqlite3` 裸 SQL，与 better-sqlite3 无关）：

```
① pull 写入后                     pulled_seq=1002  pushed_seq=0
② push 写入后（现行代码）          pulled_seq=0     pushed_seq=1011   ← 清零
③ 同一场景，修法                   pulled_seq=1002  pushed_seq=1011   ← 正确
```

## 3. 逐项设计

### V1 —— 游标 upsert 改命名参数

**改法**（`engine.ts:156-171`）：用命名参数在 DO UPDATE 里直接引用**绑定值**，
而不是引用被 COALESCE 污染过的 `excluded`：

```sql
INSERT INTO sync_cursor (endpoint, pulled_seq, pushed_seq, updated_at)
  VALUES (@endpoint, COALESCE(@pulled, 0), COALESCE(@pushed, 0), @now)
ON CONFLICT(endpoint) DO UPDATE SET
  pulled_seq = COALESCE(@pulled, sync_cursor.pulled_seq),
  pushed_seq = COALESCE(@pushed, sync_cursor.pushed_seq),
  updated_at = @now
```

**为什么不用 `NULLIF(excluded.x, 0)`**：能跑通（§2 的 ③ 验证过），但引入「0 是哨兵值」的
歧义 —— 真要把游标写成 0（重置场景）就会被当成「没传」。命名参数没有这个坑。

**必须连注释一起改**：`engine.ts:148-155` 那段 doc comment 现在声称
*"subsequent calls preserve the opposite column via `COALESCE(excluded.*, sync_cursor.*)`"* ——
**这正是本轮证明为错的机制**。只改 SQL 不改注释，等于给下一个维护者留一个「按注释理解就会重犯」的坑。
新注释要写清：保留另一列靠的是 **DO UPDATE 直接引用绑定参数**，
而 VALUES 里的 `COALESCE(@x, 0)` 只负责满足 `NOT NULL`、**绝不能**再被 `excluded` 读到。

**不需要 migration**：schema 不动。存量库的 `pulled_seq` **可能**正停在 0（取决于最后一轮是以
pull 还是 push 收尾）—— 若是，升级后第一轮会做**最后一次**全量重放然后自愈；若不是则无此轮。
写 release notes 时按「可能」措辞，不要写成「一定」。

**回归用例**（补 §1.6 的空白，`engine.test.ts`）：
1. pull 轮 → push 轮 → 断言 `pulled_seq` **仍是** pull 写入的值；
2. push 轮 → pull 轮 → 断言 `pushed_seq` 仍在；
3. 直接对 `upsertSyncCursor` 做单元测试：只传 pulledSeq / 只传 pushedSeq / 两个都传 / 首次插入；
4. **显式写 0**：`upsertSyncCursor(sqlite, ep, { pulledSeq: 0, nowMs })`（`nowMs` 是必填字段，
   初稿的示例漏了）必须真的把 `pulled_seq` 写成 0，
   而不是被当成「没传」保留旧值 —— 这条守住「不把 0 当哨兵」的设计理由，
   也是不采用 `NULLIF(excluded.x, 0)` 的可执行依据。

### V2 —— 同步轮次可观测性

> ⚠️ **初稿错在哪**：① `RunSyncLogger` 只有 `info` / `warn`，没有 `debug`（`engine.ts:97-100`），
> 直接把 `logger.info` 改成 `logger.debug` 通不过 typecheck；② `trigger` 不能是一个模块级全局字符串 ——
> coalescer 会把并发调用合并成「当前轮 + 一个 follow-up」两个槽（`coalesce.ts:36-62`），
> SSE / outbox / scheduler 并发时单个 `currentTrigger` 会错标轮次；
> ③ summary 漏了 `duplicatesTotal` 和 `serverSeqHigh`，而 `pushedTotal` 只数 accepted，
> **不含 duplicate ack**（`engine.ts:358-360`），所以初稿那组字段并不是「完整数字」。

**V2-a 给 `RunSyncLogger` 加 `debug`**（`engine.ts:97`）：

```ts
export interface RunSyncLogger {
  info: (...a: unknown[]) => void;
  warn: (...a: unknown[]) => void;
  debug: (...a: unknown[]) => void;   // 新增，必填而非可选
}
```

要补的实现有三类（初稿只说了第一类）：
1. 生产 adapter：`manual.ts:243-246`，补一行 `debug` 绑到 `ctx.logger.debug`；
2. **core 内的 `NOOP_LOGGER`（`engine.ts:187-190`）** —— 漏了它会直接 typecheck 失败；
3. `engine.test.ts` / `apply` 相关测试里的 fake logger，一并补齐。
**选必填不选可选**，是为了不让调用点写成 `logger.debug?.(…)` —— 那样漏实现不会报错。

**V2-b 逐条日志降级**：`apply.ts` 的 `apply note …` / `apply folder …` / `pull skip …`
全部 `info → debug`。修完 V1 后量级本来就会掉 ~50 倍，但 per-change 的 info 本身就不该是默认级别。

**V2-c round summary**（`manual.ts` 的 `doRunManualSync` 成功分支），info 级：

```ts
ctx.logger.info(
  { kind: 'sync', triggers,                       // string[]，见 V2-d
    cursor_before: r.cursorBefore, cursor_after: r.cursorAfter,
    pulled: r.pulledTotal, applied: r.appliedTotal, skipped: r.skippedTotal,
    pushed: r.pushedTotal, duplicates: r.duplicatesTotal,
    server_seq_high: r.serverSeqHigh, conflicts: r.conflictsRecorded },
  'sync round done',
);
```

这些字段 `runSync` 本来就全都返回了（`engine.ts:370` 附近），**只是没有任何一处打出来**。

⚠️ **「一轮」的口径要写死**：summary 只在成功分支输出，而**一次 401 恢复会在同一个 coalescer
逻辑轮里跑两次 `attemptSyncRound`**（`manual.ts:328` 与 `:335`，中间夹 `maybeRecoverCloudSession`）。
所以 `sync round done` 的条数 = **成功完成的 coalescer 逻辑轮次数**，不是 `attemptSyncRound` 的调用次数，
也不含失败轮。若日后想让失败也可计数，需要另加一条 `sync round failed`（本轮**不加**）。

**V2-d trigger 归属到 coalescer 槽**：`createCoalescer` 目前是 `run(): Promise<R>`、
`runner: () => Promise<R>`。改成每个槽各自累积一个 trigger 集合：

- `run(trigger: SyncTrigger)`：若无 inflight → 开新槽，集合 = `{trigger}`；
  若有 inflight 且无 follow-up → 建 follow-up 槽，集合 = `{trigger}`；
  若 follow-up 已存在 → **并入 follow-up 的集合**（这是初稿会错标的那一格）；
- `runner(triggers: SyncTrigger[])`：`start()` 时把该槽的集合交给 runner 并清空。

`SyncTrigger = 'sse' | 'sse-reconnect' | 'scheduler' | 'outbox' | 'manual'`，
五个调用点（`sse-bridge.ts:166` 的 onChange、onOpen 的 catch-up、`scheduler.ts`、
`outbox-watcher.ts`、HTTP 路由）各传各的。

**并发用例**：inflight 期间连发 `sse` + `outbox` + `scheduler`，断言只跑两轮、
且第二轮的 `triggers` 是三者中后两个的集合，不是最后一个覆盖前面的。

> 判据：这条 summary 如果三周前就在，V1 第一天就会被发现 —— `cursor_before: 0` 一眼可见。

### V4 —— 元数据 op 跨设备生效

只有两种：`{pinned_at_ms}`（置顶）和 `{position}`（排序）。

**设计选择：不给它们上 LWW，按 `server_seq` 到达顺序应用。**

理由：这两个字段与正文无关、丢一次代价极低，而给它们加 `updated_at_ms` 会把它们卷进
**行级 LWW** —— 一次置顶就会抬高整行的 LWW 键，让另一台设备并发的**正文编辑**判负。
那是把一个显示层问题升级成数据丢失风险，不划算。

**⚠️ wire payload 字段名 ≠ db 列名**（初稿在这里写错了，照初稿写 SQL 会直接
`no such column: pinned_at_ms`）：

| 概念 | wire payload（`sync_changes.payload`） | SQLite 列（`schema.ts`） |
|---|---|---|
| 置顶 | `pinned_at_ms`（number \| null） | **`notes.pinned_at`**（`:44`，`integer(timestamp_ms)`，NULL = 未置顶） |
| 排序 | `position`（number） | **`notes.position`**（`:47`，**REAL**，nullable；首次 reorder 才materialise 成 1000/2000/…） |

**改法**（`apply.ts:545-554` 那个分支）：

- **严格校验 op + payload 形状**，不能只判断 key 存在：
  - `op === 'pin'` 且 payload 恰为 `{pinned_at_ms: 有限 number | null}` → 写 `notes.pinned_at`；
  - `op === 'update'` 且 payload 恰为 `{position: 有限 number}` → 写 `notes.position`；
  - 其余（含 `NaN` / `Infinity` / 多余 key / 未知形状）→ 维持现有 skip + 日志（降 debug）。
- 两者都**不动** `updated_at` / `updated_at_ms` / `lww_counter`，不进 `observeRemoteLwwKey`；
- **本地行不存在时**：`UPDATE` 影响 0 行 → 返回 `'skipped'`，不报错（这是 §V4 历史状态那一节的场景）。

**不会 ping-pong**（已核实）：`notes.pinned_at` / `notes.position` 上没有往 `sync_changes` 写的触发器 ——
现有触发器只有 content FTS 同步和 `local_device_uuid` 约束。outbox 行由业务层 `emitSyncChange` 显式追加，
apply 路径不经过它。

#### ⚠️ 不变量：metadata 的 own echo **必须应用**，不能走 self-replay skip

`applyOneNoteChange` 的 metadata 分支（`apply.ts:548`）在 `parseNotePayload` 之前，
因此**位于 `isSelfReplay` 检查（`apply.ts:252`，在 `applyNoteChange` 里）之前**。
这个位置今天是「碰巧对」的，本轮要把它写成显式不变量并加测试，否则实现者很容易
按「走和现有远端 apply 相同路径」把它挪到 self-replay 之后，从而引入下面这个永久分歧：

```
① A 本地已有一次尚未 push 的新排序 X
② 同步轮先 pull（engine.ts:309 的顺序是 pull 在前、push 在后），
   拉到 B 的旧排序 Y → 按到达顺序应用 → A 本地被覆盖成 Y
③ 同轮 push，A 的 X 拿到更大的 server_seq，服务器与 B 最终都是 X
④ 下一轮 A 拉到自己的 own echo X
     ├─ 应用   → A 也回到 X，三方一致 ✅
     └─ skip   → 服务器和 B 是 X，A 永久停在 Y ❌
```

**自动化用例**（不是只做真机验收）：构造「pull 旧远端 → push 本地新值 → own echo」三步，
断言最终三方一致；并显式断言 metadata 分支在 `isSelfReplay` 之前被命中。

#### V4a 口径：只保证 0.6.3 之后新产生的 metadata op

**历史状态不会被自动修复**，原因链（已核实）：

- 旧库确实存在「先有 `pin`/`update`，`create` 是 `0008` 后补的」这种顺序
  （`0008_backfill_create_ops.sql:6-14` 自己记录了这个问题）；
- 而 `create` 的 payload **不含** `pinned_at_ms` / `position`（`emission.test.ts:91-93` 断言了这点）；
- 已同步设备的 cursor 早已越过那些旧 metadata op，不会重新投递；
- 新设备可能先收到 metadata op 而 note 还不存在 → `UPDATE` 影响 0 行；随后的 `create` 又不带这两个字段。

⇒ **0.6.3 之后新发生的置顶/排序会跨设备生效；升级之前既有的置顶/排序状态不会自动对齐。**
这句话原样写进 `docs/history/0.6.3-release-notes.md`。

#### V4b 一次性 current-state re-emit —— **本轮删除，不做**

初稿把它写成「可选」，但 §0 和 release notes 又已经引用它，实施范围其实没定。
第二轮审阅进一步指出这个设计本身也不完整，**四个洞都是真的**：

- 权威设备 `pinned_at IS NULL`、另一台仍置顶 → 扫描条件 `IS NOT NULL` 根本不发 unpin，对齐不了；
- `position IS NULL` 同理，清不掉另一台的旧值；
- 一行同时有 pin 和 position 时需要**两条** op，「补发一条」有歧义；
- 要发 unpin/清 position 就得让 apply 侧接受 `position: null`，而 V4a 的校验只收有限 number。

要做对，就得是「扫描全部目标 notes × 每行分别发 pin 和 position（含 null）× 单事务 ×
dry-run × 确认机制 × 大批量 outbox 的体量评估 × CLI 还是 route 二选一」——
这是独立一项工程，不该混在本轮里半成品交付。

**决定：0.6.3 只保留 V4a 的口径**（只保证 0.6.3 之后新产生的 op）。
存量状态要对齐，用户在**一台**设备上重新拖一遍 / 重新点一次置顶即可 —— 这本来就是最小代价。
若日后确有需求，另开一项设计。

**并发语义**：两台设备同时拖拽排序，后到达服务器的赢。可接受。
**FTS**：这两个字段不进 FTS，无需同步 `tags_text` / content 索引。

**量级**：`reorder` 是**按列表逐条**发的（`notes/index.ts:786` 的 `for` 循环，
`position = (i+1)*1000`），一次拖拽 = N 条变更。真机日志佐证：一天 392 条 `op=pin` +
3683 条 `op=update`（后者绝大多数是 reorder）。所以 V4 落地后接收侧每次拖拽会产生 N 次
`UPDATE notes SET position`。都在同一个 pull 批次的事务里，成本可接受，但实现时
**不要给每条 apply 加 info 日志**（V2-b 已统一降 debug）。

**测试**（不能只靠真机）：
1. **替换**现有那条「metadata op 必须被 skip」的单测 —— 它现在断言的是要被推翻的行为；
2. 单测：pin/position 各自的 apply（**含 `pinned_at_ms: null` 的取消置顶**）、
   本地行不存在 → 0 行 skip、坏 payload → skip。每个 apply 用例都要**显式断言副作用边界**：
   - `notes.updated_at` / `notes.lww_counter` / `notes.device_id` **均未变**
     （⚠️ **`notes` 表没有 `updated_at_ms` 列** —— 那是 wire payload 的字段名，初稿写错了；
     行级时间戳列是 `updated_at`，见 `schema.ts:31`）；
   - **HLC 未推进**：`local_metadata` 的 `hlc_last_ms` / `hlc_last_counter` 不变
     （`hlc.ts:31-32`）—— 这是「不进 `observeRemoteLwwKey`」的可执行判据；
   - `sync_changes` **没有新增行**（钉死「不回写 outbox」）；
3. own echo 不变量用例（见上）；
4. **dual-profile e2e**：A 置顶 + 拖拽 → B 同步后一致；A/B 各改一次 → 以 server_seq 大者收敛。

| V1 | 建一条笔记 → 观察下一轮 round summary：`cursor_before` = 上一轮的 `cursor_after`，`pulled` = 1（自己那条）或 0，**不是 1000** |
| V1 | 连做 5 次「本地写入 → 等同步」，`sync_cursor` 的 `pulled_seq` 与 `pushed_seq` **同时**保持单调不减 |
| V1 | `GET /sync/status` 的 `pushed_seq` 不再恒为 0 |
| V2 | **不用日志体积做判据**（体积跟使用量强相关）。改为断言：info 级的 per-change 日志条数 = **0**；`sync round done` 的条数 = **成功完成的 coalescer 逻辑轮次数**；每条都带完整 **9** 个数字（两个 cursor + pulled/applied/skipped/pushed/duplicates/server_seq_high/conflicts） |
| V4 | 桌面置顶/拖拽 → 网页端刷新后一致；网页端改 → 桌面一致。⚠️ **只验升级后新做的操作**；升级前既有的置顶/排序不对齐是预期行为（§V4a） |
| V3 | `pm2 restart owl-server` 后不登录：首条 `{kind:'session-watchdog', reason:'no_session'}` level-40 日志落在 **10–11 分钟窗口**内（检测是 60s 轮询 + 事件循环抖动，写「10 分钟内」是保证不了的；要精确就得改成一次性 10 分钟 one-shot timer）；`curl /status \| jq .data.sync` 得到 `session_installed:false, state:'login_required'`；登录后 watchdog 收敛且不再报 |
| W2 回归 | 修完 V1 后裁剪不再被 `pulled_seq=0` 挡住 —— 云端 2026-08-19 复验时 `推算已裁行数 > 0`。**✅ 2026-08-27 复验通过：推算已裁 12 / 该裁未裁 0，见 §9** |

## 7. 风险 / 明确不做

- **V1 改的是同步最核心的一条 SQL**。风险控制：三个方向的回归用例（§V1）+ 门禁全绿 +
  真机连续 5 次写入观察游标单调性。改动本身是 4 行 SQL，不涉及控制流。
- **V4 的「不上 LWW」是一个明确取舍**：并发排序以到达顺序定胜负，不保证两端语义完全一致。
  若日后要严格一致，需要的是 **per-field server seq**（每个字段各记一个已应用的 server_seq），
  那是独立设计题，不在本轮。
- **V4 最容易被实现坏的一点**：metadata own echo 必须应用。分支位置（在 `isSelfReplay` 之前）
  今天是碰巧对的，本轮把它固化成不变量 + 用例；review 时重点看这里有没有被「顺手统一路径」挪走。
- **V4 不修复历史状态**是本轮的显式口径，不是遗漏。批量修复通道（原 V4b）第二轮审阅后
  **已删除** —— 它的扫描条件对 unpin / 清 position 根本不成立，做对需要独立一项工程。
- **V3 不落盘云端凭据**，重启后仍需人工登录一次 —— 本轮只让它「可被发现」，不让它「自动恢复」。
- **不做**：V5 存量行清理 · D9（含同步痕迹的 local 库要不要禁止 claim merge，仍未拍板） ·
  TLS/反代（A1，独立一轮）· skybridge EventBus 跨进程总线（跨仓）。
